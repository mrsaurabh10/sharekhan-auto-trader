# Strategy instances and shared risk controls

Implemented October 19, 2026. Publication does not activate a strategy or deploy it.

## Instance identity and closing

Each subscription has independent runs. Expiry straddles use an AM and a PM run
per trading date; other templates use one run per subscription/trading date,
including all symbols generated by universe/list strategies. Direct evaluations
use account, broker, template, configured symbol and trading date/session.
A run is created only when preparing an entry. Settings and lots are frozen at
creation. Changing a subscription affects subsequent runs.

The personal Orders screen and admin executed-trade section show expandable
instances, complete child trades, realized/open/combined gross P&L, estimated
charges/net, peak and active stop floor. Pagination selects runs before loading
all their legs. Manual and historical unlinked trades remain in individual tables.
Older records are not automatically assigned to runs from source labels.

**Close this instance** sends one action, with no second confirmation dialog.
It first persists OPEN → CLOSING, blocks further entries/retries for that run,
cancels unsubmitted entries, requests broker cancellation of pending entries,
and squares off filled positions through the existing exit-order machinery.
Existing exit order IDs remain authoritative. One failed leg does not prevent
attempting the others. Acknowledgements and unknown/partial submissions keep the
run CLOSING; only resolved entries and confirmed terminal positions permit CLOSED.
A scheduled market-time reconciler continues independently of the browser.
Restart retains close intent, peak, floor and membership. Existing broker polling
and exit-chase recovery limitations still apply; unknown exposure needs reconciliation.

Closing AM does not pause its subscription or close PM. **Close all & pause
strategy** cancels that subscription first and latches all its open runs for exit.
Run creation locks the subscription row to serialize with cancellation. Evaluation
outcomes update only active subscriptions, so a stale evaluator cannot restore a
cancelled subscription. The existing Cancel subscription action still stops future
evaluations without closing current positions.

API: GET `/api/strategies/runs` (page/size, admin optional userId), POST
`/api/strategies/runs/{id}/close`, POST
`/api/strategies/subscriptions/{id}/close-and-pause`. Close actions require session
CSRF and authenticated account ownership (admin may manage selected accounts).
Run IDs on entry requests and subscription IDs on evaluations are server-owned;
JSON clients cannot assign them. Trades, requests and related execution audit
events retain explicit run IDs, including staged/partial trade copies.

## Shared rupee rules

Configure optional `riskSettings` when starting a strategy. Amounts use TOTAL or
PER_LOT; the latter multiplies by captured configured lots, never by summed lots
across CE and PE or symbols. Cash mover strategies require TOTAL.

| Setting | Rule |
| --- | --- |
| profitTarget | Close when combined gross P&L reaches this amount |
| maxLoss | Initial stop floor is negative maximum loss |
| trailActivation + trailGiveback | After peak reaches activation, floor is peak minus giveback |
| slStepProfit + slStepRaise | Raise initial loss floor by stop raise for every whole profit step reached by peak |

The highest applicable floor wins and never decreases. Equality triggers exit.
Blank/zero disables a setting. Profit-trail fields must be paired, giveback must
be less than activation. Stepped SL needs maxLoss and both step fields; raise
cannot exceed profit step. A fixed target must exceed trail activation if both
are enabled. All amounts are nonnegative, max 999999999.99 with two decimals.
Example: PER_LOT target 2000 with two lots exits at combined gross 4000 for each
run. Total maxLoss 1000, SL profit step 500 and raise 250 gives floors -1000 at
zero peak, -500 at peak 1000, and zero at peak 2000. Profit trail activation 2000
and giveback 500 raises the floor to 1500 at peak 2000 and 2500 at peak 3000.

Risk checks use confirmed actual entry fills and fresh uncrossed liquidation
books (bid for longs, ask for supported cash shorts), <=5 seconds old and <=2
seconds between books. Missing marks display unavailable and skip automatic
P&L decisions. Straddle checks require both full equal-sized executed CE/PE legs;
paired-entry recovery and scheduled exits remain independent of optional rules.
Gross combines realized and open P&L. Costs/net are estimates from the existing
long-only fee model; unsupported short fees show unavailable. Exit price/slippage
can move realized returns beyond the trigger amount. Polling is approximately
one second while the app is running during market hours, not an exchange stop.
Individual leg stops and timed exits remain independent and can close earlier.

Legacy `profitTargetPerLot` straddle subscriptions remain supported when shared
rules are absent; pre-existing unlinked sessions retain their legacy monitor.
The common form replaces the dedicated straddle profit field for new settings.
The pure risk engine accepts marks for future replay integration; existing timed
NIFTY studies have not been rerun as a generalized trailing-risk backtest.

## Rollout and validation

No production DDL, broker action or deployment was performed. For a separately
authorized rollout review/apply expiry-straddle-schema.sql, then
straddle-profit-target-schema.sql, then strategy-run-schema.sql in
`src/main/resources/db/postgresql/` on the primary trading database before startup.
The audit schema also adds strategy_run_id for a separately configured PostgreSQL
audit store. Existing source-copy migration tooling does not migrate run lifecycle
or risk snapshots; use a complete database migration for installations with runs.
Do not infer memberships during a historical import.

Tests cover risk boundaries/scaling/monotonic floors, AM/PM identity and frozen
settings, ownership/CSRF, complete grouping, repeated close, pending/late fills,
unknown submissions, independent leg errors, entry membership, and cancellation
races. Browser verification uses mocked APIs and isolated Chrome; no real order
is submitted. See current project handoff for exact test counts and publication.
